## Primary Dataset — customer_churn.csv

### Original Features

| Column | Data Type | Role | Description | Possible Values / Range |
|---|---|---|---|---|
| `CustomerID` | string | Identifier | Unique customer identifier. Not used as a predictive feature. | C00001 – C00500 |
| `Tenure` | int | Feature | Number of months the customer has been with the company. | 1 – 71 months |
| `MonthlyCharges` | int | Feature | Amount the customer is charged per month in dollars. | \$20 – \$199 |
| `TotalCharges` | int | Feature | Cumulative amount the customer has been charged (Tenure × avg monthly rate). | \$159 – \$7,992 |
| `Contract` | string (categorical) | Feature | The type of contract the customer holds. | Month-to-month, One year, Two year |
| `PaymentMethod` | string (categorical) | Feature | How the customer pays their bill. | Credit Card, Electronic Check, Bank Transfer |
| `PaperlessBilling` | string (categorical) | Feature | Whether the customer has opted for paperless billing. | Yes, No |
| `SeniorCitizen` | int (binary) | Feature | Whether the customer is a senior citizen. | 0 = No, 1 = Yes |
| `Churn` | int (binary) | **Target** | Whether the customer churned (cancelled service). | 0 = No Churn, 1 = Churned |

### Column Notes

- **CustomerID**: Stripped from all model inputs. Used only for joining predictions back to customers.
- **SeniorCitizen**: Encoded as integer (0/1), not "Yes"/"No" — unlike PaperlessBilling.
- **TotalCharges**: Correlated with Tenure × MonthlyCharges. Engineered features derived from it capture this more explicitly.
- **Churn**: Severely imbalanced — 89.4% No Churn, 10.6% Churn. Requires `class_weight='balanced'` in models.

## Engineered Features (created in `src/feature_engineering.py`)

| Feature | Formula | Data Type | Business Meaning |
|---|---|---|---|
| `AverageMonthlySpend` | `TotalCharges / max(Tenure, 1)` | float | Smoothed monthly spend; corrects for varying tenure. Differs from MonthlyCharges when customers change plans. |
| `ChargesPerTenure` | `MonthlyCharges / max(Tenure, 1)` | float | Cost pressure relative to tenure length. High ratio = paying a lot for a short relationship. |
| `EstimatedCLV` | `MonthlyCharges * Tenure` | float | Approximate total revenue generated by the customer (Customer Lifetime Value proxy). |
| `TenureGroup` | Bins of Tenure: New(1-12), Growing(13-24), Established(25-48), Loyal(49+) | string | Lifecycle stage category. Enables non-linear tenure effects without ordinal assumptions. |
| `ContractRisk` | `1 if Contract == "Month-to-month" else 0` | int (binary) | Direct churn risk flag from contract type. Month-to-month = zero switching cost. |
| `PaymentRisk` | `1 if PaymentMethod == "Electronic Check" else 0` | int (binary) | Electronic check correlates with elevated churn. May indicate payment friction or dissatisfaction. |
| `HighChargeFlag` | `1 if MonthlyCharges > 75th percentile else 0` | int (binary) | Flags above-average spend customers. High spenders who churn = highest revenue impact. |
| `CustomerValueSegment` | Tercile of MonthlyCharges: Low / Medium / High | string | Revenue tier for differentiated retention strategy. |

### Feature Engineering Decisions

- **Why AverageMonthlySpend instead of just MonthlyCharges?** MonthlyCharges reflects the current rate; AverageMonthlySpend reflects the overall financial relationship including historical pricing.
- **Why ChargesPerTenure?** A customer paying \$100/month for 2 months vs. 60 months is in a very different relationship with the company.
- **Why binary flags for Contract and Payment?** Allows the model to weight these specific high-churn categories even when using ensemble methods that handle categoricals natively.
- **Not created**: Features requiring external data (macroeconomic, competitor pricing), features requiring future data (leakage), or features from TotalCharges alone (collinear with Tenure × MonthlyCharges).
